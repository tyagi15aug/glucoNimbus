# ADR 0012: Auth — Credentials + JWT sessions, three-role model

## Status

Accepted. Built in Phase 4.

## Context

Spec Section 13 asks for authentication and authorization. The schema
already reserved a `users` table (empty, unused) with a `role` column
(`USER | DEVELOPER | ADMIN`) back in Phase 3, anticipating this. Phase 6's
failure-injection control panel needs *something* to gate it — an
unauthenticated developer panel that can flip on "drop 20% of readings" or
"take the database down" for anyone who finds the URL isn't a real
demonstration of authorization, it's a liability.

## Decision

**Credentials (email + password) over OAuth.** This is a self-contained
portfolio demo with no third-party identity to federate against — adding
Google/GitHub OAuth would mean registering an OAuth app, managing client
secrets, and a callback flow, for a login system that exists to
demonstrate the pattern, not to onboard real users. Credentials is the
honest choice here, not a corner cut.

**JWT session strategy, no separate `sessions` table.** The signed token
*is* the session — `sub` (user id), `email`, `role`, a 7-day expiry,
HS256, verified against `AUTH_SECRET`. Accepted trade-off: there is no
server-side revocation. Logging out just deletes the cookie client-side;
a copied/stolen token stays valid until it expires. A production system
with real user data would need a denylist or short-lived
access+refresh-token pair; this one doesn't carry data worth that
complexity, and the spec doesn't ask for it.

**`jose` for JWTs, `bcryptjs` for password hashing** — both pure
JavaScript, zero native bindings. This matters concretely here: ADR
0007 already hit a wall with Prisma's native binary download being
blocked by this sandbox's egress policy, and the canonical `bcrypt`
package (as opposed to `bcryptjs`) needs a native compile step too. Using
pure-JS libraries for both sidesteps that failure mode entirely, and as a
bonus keeps JWT verification usable from Next.js Middleware, which runs
on the Edge runtime (no Node APIs, no native modules) — see the next
point.

**Password verification (`lib/password.ts`, bcryptjs) is split from
session verification (`lib/jwt.ts`, jose).** Middleware only ever needs
to verify a token, never hash a password, so keeping `lib/jwt.ts` free of
any bcryptjs import keeps it Edge-safe. `lib/session.ts` (the
`next/headers`-based helpers for Server Components/Route Handlers) builds
on `lib/jwt.ts`, not the other way around.

**Role model is a simple hierarchy (`USER < DEVELOPER < ADMIN`), not a
permission set.** `hasRole(session, minimum)` checks rank, not named
capabilities — there's exactly one gated area today (`/developer`,
requiring `DEVELOPER`), so a full RBAC/permission-list system would be
speculative. `ADMIN` exists in the schema and type today with nothing
that specifically requires it yet — reserved for exactly this reason,
not built out further until something needs it.

**Self-registration always creates `USER`-role accounts.**
`DEVELOPER`/`ADMIN` accounts are never reachable through
`POST /api/auth/register` — the only way to get one today is
`npm run db:seed-demo-user` (creates `demo@gluconimbus.dev`, documented in
the README). There's no admin UI to promote a user yet; that's a
reasonable Phase 6/10 follow-up, not a Phase 4 requirement.

**What's protected, what isn't.** The dashboard, analytics, and every
existing read endpoint stay unauthenticated on purpose — this is a
portfolio demo, and gating the actual point of the project (watching
simulated readings flow through) behind a login would hurt, not help,
its purpose. `middleware.ts` protects `/developer/*` only
(`matcher: ["/developer/:path*"]`); Phase 6's failure-injection API
routes will need the same `getSession()`/`hasRole()` check server-side
when they're built (middleware alone isn't a substitute for checking on
the route handler too, for anything that isn't purely page navigation).

## Consequences

- No password reset flow, no email verification, no rate limiting on
  login attempts. Documented gaps, not oversights — each is a real
  feature with its own scope, and none of them is what Section 13 is
  actually asking this project to demonstrate (the pattern: hash
  passwords, never store them plain; sign and verify sessions; gate a
  route by role). A production system handling real user data would need
  all three before shipping.
- `AUTH_SECRET` must be set (`.env.example` documents it, plus
  `openssl rand -base64 32` to generate a real one) — `lib/jwt.ts` throws
  loudly if it's missing rather than silently signing with `undefined`.
- Changing a user's role (once an admin UI exists to do it) won't take
  effect until their existing JWT expires (up to 7 days) unless they log
  out and back in — an inherent property of stateless JWT sessions, not a
  bug to fix later.
