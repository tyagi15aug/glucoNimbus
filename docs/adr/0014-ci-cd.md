# ADR 0014: Phase 9 — GitHub Actions CI, and what "IaC" means here

## Status

Accepted. Built in Phase 9.

## Context

Spec Section 24 lists Phase 9 as "CI/CD and IaC." The Master Plan's shared
CI/CD standard (Section 14) is:

```text
Checkout -> Install -> Lint -> Typecheck -> Unit tests -> Build -> E2E tests -> Upload artifacts
```

and Section 8 defines a shared CI-artifact contract (`metadata.json` plus a
`logs/` directory, at minimum) so an external "AI CI Analyzer" project could
later consume this repo's CI output — that analyzer is explicitly a separate
project (Section 11, "Repository Independence"; `claude/phase-1-progress.md`
records that CloudLab's in-repo analyzer phase was pulled out for the same
reason). GlucoNimbus's own obligation is just to produce artifacts in that
shape, nothing more.

## Decision: one workflow, two jobs

`.github/workflows/ci.yml` runs on push and PR to `main`:

- **`checks`** — install, lint, typecheck, unit tests (vitest, against a
  real `postgres:16-alpine` service container — same "no mocking the DB"
  convention as the test suites themselves), build.
- **`e2e`** (`needs: checks`) — the Phase 7 Playwright suite, against its
  own Postgres service container.

Splitting into two jobs means a lint/typecheck/build failure (cheap, fast)
doesn't wait behind or get bundled with the slower Playwright run, and
`needs: checks` means the E2E job doesn't spend runner time at all when the
fast checks already failed.

Both jobs write a `ci-artifacts/metadata.json` (repository, commit, branch,
workflow, job, run id, status, timestamp — the exact shape Master Plan
Section 8 sketches) and `tee` every command's output into
`ci-artifacts/logs/`, uploaded via `actions/upload-artifact` even when the
job fails (`if: always()`) — a red run's logs are the ones actually worth
keeping. The `e2e` job additionally uploads Playwright's own HTML report and
trace output as a separate `playwright-report` artifact, left in Playwright's
native layout (not folded into `ci-artifacts/`) so a downloaded copy still
opens with a plain `npx playwright show-report`.

### No LocalStack service in CI

`docker-compose.yml`'s LocalStack service can't be reused directly as a
GitHub Actions `services:` container: service containers start before
`actions/checkout` runs, so `infrastructure/localstack/init`'s bootstrap
script (mounted as a volume in docker-compose) has nothing to mount from —
the repo isn't checked out yet. Standing LocalStack up in CI would mean
`docker run`-ing it as an ordinary step instead, after checkout, and
teaching that step to wait for health + run the init script itself.

That's real, buildable work, but it wasn't done here, on purpose: the Phase
7 E2E suite (`apps/web/e2e/api/readings.spec.ts`) already treats a
missing LocalStack as an expected, asserted-on outcome (`503
QUEUE_UNAVAILABLE`), not a gap to paper over — see the README's Testing
section. Standing up LocalStack in CI would mean rewriting those
assertions to expect the *other* branch instead of adding coverage, for a
non-trivial chunk of CI plumbing. If real SQS/S3 wiring ever needs to be
exercised in CI specifically (as opposed to locally, where it already can
be via `docker compose up`), that's a real follow-up, not a silent gap —
recorded here rather than left unstated.

### `AUTH_SECRET`

`.env.example`'s `AUTH_SECRET` is placeholder text, not a real secret
(that gap is what caused the production bug fixed this session — see the
progress doc's Session 12 entry). CI generates a real one
(`openssl rand -base64 32`) per run rather than committing a fixed test
secret to the repo or to `.env.example`.

### A pre-existing bug this surfaced

Wiring up `npm test` at the repo root for the first time (previously only
ever run per-workspace) surfaced that `apps/simulator` has a `test` script
(`vitest run`) but zero test files, which vitest treats as a failure by
default ("No test files found, exiting with code 1") — this would have
broken `checks` on the very first CI run for a reason unrelated to any
real bug. Fixed by adding `--passWithNoTests` to that one script rather
than removing it, so a future simulator test file is picked up by the
existing wiring with no changes needed, and `npm test` accurately reflects
"no tests exist yet here" instead of failing.

## Decision: IaC means Render's blueprint and LocalStack's init scripts, not new Terraform

The spec pairs "CI/CD" with "IaC" in the same phase, but this repo already
has two things that are infrastructure-as-code in the literal sense, both
predating this phase:

- `render.yaml` — a Render Blueprint, which is exactly what it sounds
  like: the `gluconimbus-web` service, its managed Postgres database, and
  LocalStack are all declared as code and applied by pointing Render's
  dashboard at the repo (`docs/adr/0010-render-hosting.md`).
- `infrastructure/localstack/init/` — the S3 bucket and SQS queue/DLQ
  bootstrap, applied automatically by LocalStack's own init-hook
  mechanism on every `docker compose up` (`docs/adr/0004-why-localstack.md`).

What's genuinely *not* code is the GCP side of the scheduled-worker setup
(`docs/adr/0011-scheduled-worker-for-hosting.md`): the Cloud Run Job, Cloud
Scheduler trigger, and IAM bindings described there were created by hand in
the GCP console, and stay that way after this phase. Writing real Terraform
for them now, in a sandbox with no GCP credentials to actually run
`terraform plan`/`apply` against, would produce a `.tf` file whose only
testing is "it parses" — indistinguishable from not having it, and worse
than the honest "**Not started**" a status table already communicates
plainly. The CloudLab plan's own "what not to build early" list
(`CloudLab Implemenation Plan.md` Section 19) names "Terraform integration"
directly for the same reason: it's a real, worthwhile addition, just not
one this phase claims to have finished.

## Consequences

- `main` now gets a real GitHub Actions run on every push and PR, covering
  everything Phase 7 already covers locally, for the first time
  automatically rather than only when someone remembers to run it by hand.
- The GCP Cloud Run Job/Scheduler/IAM setup remains manual and
  undocumented-as-code; a future Terraform pass is a real, scoped follow-up,
  not a silent gap.
- This is also the first phase whose actual success can only be confirmed
  once Anuj pushes from his own machine — the sandbox has no path to GitHub
  Actions itself (see the progress doc's recurring `device_bash`
  host-key-verification notes). Everything above the "push" step (that the
  workflow YAML is valid, and that every command it runs is one that has
  actually been run successfully in this session) is as far as this phase
  can be verified from here.
