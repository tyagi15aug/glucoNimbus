# ADR 0009: Cloudflare as the public deployment target

## Context

`GlucoNimbus` runs today as Node processes against local Postgres/LocalStack (ADR 0004, ADR 0008). Anuj wants a public, low-cost, always-reachable demo of it — the uploaded deployment plan ("GlucoNimbus — Cloudflare Deployment & Architecture Plan") sets Cloudflare as the target while keeping LocalStack for local dev. This ADR records what that plan got right, what it glossed over, and the concrete choices made instead — verified against Cloudflare's live documentation and this account's actual state (via the Cloudflare Developer Platform MCP connector), not assumed from training knowledge that could be stale for a fast-moving platform.

## What the original plan got right

- **"Preserve architectural behavior, not vendor implementation"** (Section 2) is the correct framing, and it turns out ADR 0008's Phase 3 package split already does most of the work Section 9's domain/application/adapters layering asks for: `apps/web` and `apps/workers` never import `pg` or `@aws-sdk/client-*` directly — they go through `packages/db` and `packages/cloud`. Adding Cloudflare support is "write a second implementation behind the same seam," not a restructure.
- Canonical event schema, idempotency via `eventId`, deterministic UUIDv5, no-24/7-simulator, cold-start-aware UX, structured observability, CI artifact contract, and "don't let GlucoNimbus depend on the AI CI Analyzer" are all already true of this codebase or straightforwardly portable. No changes needed to those.

## What the plan glossed over, and what's true instead (verified, not assumed)

1. **Postgres from a Worker needs Hyperdrive.** Cloudflare Workers have no raw TCP socket access without it. Confirmed via Cloudflare's own current docs: `pg` (the driver this project already uses) works unchanged against Hyperdrive — `new Pool({ connectionString: env.HYPERDRIVE.connectionString })` — with `compatibility_flags: ["nodejs_compat"]` set. `packages/db`'s existing `createPool(connectionString?)` factory (built in Phase 3, before Cloudflare was even in scope) already supports this call shape; no change to `packages/db` was needed. What Hyperdrive does NOT give you is a place to hold a `Pool` singleton across requests — Workers are stateless per-invocation, so `apps/workers-cf` builds a fresh `Pool` per queue batch and closes it in a `finally`, rather than reusing `packages/db`'s Node-side module-level singleton.
   - **Open item**: Hyperdrive proxies to a real external Postgres — Cloudflare doesn't host one. Recommending **Neon** (generous free tier, the pairing Cloudflare's own tutorials use) as the default; easy to point Hyperdrive elsewhere later if there's a reason to.

2. **SQS → Cloudflare Queues is a real adapter, not a config swap — but a small one.** Verified the actual JS API: a producer calls `env.QUEUE.send(body)`; a consumer Worker exports `queue(batch, env, ctx)`, calls `message.ack()`/`message.retry()` per message, and `dead_letter_queue` + `max_retries` in `wrangler.jsonc` does the DLQ redrive — closely mirroring the SQS `maxReceiveCount` redrive policy already built for LocalStack. Because `apps/workers`' actual business logic was already isolated behind `processMessage()` (ADR 0008), pulling it out into a new runtime-agnostic package (`packages/ingestion`) and writing a ~70-line Cloudflare consumer (`apps/workers-cf`) around it was the whole cost — not a rewrite.

3. **S3 → R2, but R2 is not yet enabled on this Cloudflare account.** Confirmed live: the R2 bucket-list API call returned `403 — Please enable R2 through the Cloudflare Dashboard`. This is an account-level toggle with no API/CLI equivalent — **Anuj needs to do this manually** (Dashboard → R2 → Enable) before a bucket can be provisioned. Once enabled, R2 exposes an S3-compatible API (the existing `@aws-sdk/client-s3`-based `archiveRawEvent()` would work close to unchanged against it), but since `apps/workers-cf` already runs inside a Worker with bindings available, it uses a native R2 binding (`env.RAW_BUCKET.put()`) instead — simpler, no SDK, no signing.

4. **The "Start Demo" on-demand simulator needs a durable primitive, not just "a serverless function."** The plan is right that the simulator shouldn't run 24/7, but a paced multi-minute replay (10x/100x speed over real wall-clock time) can't run as a detached background task off an HTTP Worker: `ctx.waitUntil()` only extends ~30 seconds past the response, nowhere near enough for a real replay window. Checked Workers' actual limits: an HTTP-triggered Worker has no hard wall-clock cap as long as a client stays connected, but this use case has no client holding a connection open. The right fit — confirmed against Cloudflare's own guidance, which explicitly points to this product for exactly this shape of problem — is **Cloudflare Workflows**: durable, step-based (`step.do()`, `step.sleep()`), up to 30 minutes per step with unlimited chained steps, survives isolate recycling. Not Durable Objects (the first instinct) — Workflows is the closer match with less hand-rolled state machinery. **Not built yet** — scoped as its own follow-up (see below), since it's genuinely new application logic (a `POST /api/simulator/start` endpoint, a `SimulatorReplayWorkflow` class, a `Device` model the current schema doesn't have), not a deployment-target swap.

5. **Next.js on Cloudflare: use vinext, not OpenNext.** This is the one place training knowledge would have actively misled — Cloudflare's current docs (dated Aug 2026) name **vinext** (a Vite plugin reimplementing the Next.js API surface) as the recommended default for new Next.js-on-Workers projects, with OpenNext explicitly demoted to "you're already on it and can't migrate yet." Ran `npx vinext check` against `apps/web` for real rather than assuming compatibility either way: **75% reported, but the only two flagged issues (`"type": "module"`, `__dirname` usage) live in `db/load-env.ts` and `db/seed.ts` — standalone `tsx` admin scripts that aren't part of the deployed app at all.** Every actual route handler, `next/server`, and `next/link` usage came back fully supported. That's a strong green light, but the migration itself (`vinext init` rewrites the build to Vite/ESM, changes how bindings are accessed — `import { env } from "cloudflare:workers"` inside route handlers instead of a module-level import) is invasive enough, and vinext is explicitly still beta, that it deserves its own dedicated pass with real `wrangler dev`/`vite dev` verification rather than being done blind in the same session as everything else here. **Not built yet.**

## Decision

Built now (this pass): `packages/ingestion` (shared, runtime-agnostic message-processing logic) and `apps/workers-cf` (the Cloudflare Queues consumer), verified via `tsc --noEmit`, the existing real-Postgres unit test suite (unchanged behavior after the extraction), and `wrangler deploy --dry-run` (bundles cleanly, resolves the Hyperdrive/R2 bindings from config). Chosen first because it's purely additive — zero changes to `apps/web`'s existing Node build or the LocalStack dev path, confirmed by `next build` still succeeding unchanged.

Deferred to a dedicated next pass, named explicitly rather than left implicit:
- The `apps/web` → vinext migration itself, with real `wrangler dev` verification against actual bindings.
- `POST /api/readings`' Cloudflare-side publish path (needs the vinext migration first to have `env` binding access inside route handlers).
- The Workflows-based on-demand simulator control surface (`/api/simulator/start|stop|pause|resume`) and the `Device` model the plan's Section 4 assumes but doesn't exist in the schema yet.
- Actual provisioning: enabling R2 (Anuj, dashboard-only), picking/creating the external Postgres (Neon recommended, pending confirmation), `wrangler queues create` x2, `wrangler hyperdrive create`, `wrangler r2 bucket create`, and a real (non-dry-run) deploy.

This is a genuinely large piece of work — comparable in size to Phases 4/6/7/9/10 combined, not a quick deployment step layered on top of them. Naming that plainly so the scope doesn't surprise anyone, per the plan's own definition-of-done checklist being closer to a second project arm than a config change.

## What's verified vs. not

**Verified for real:** `packages/ingestion` typechecks and is imported correctly by both `apps/workers` (unchanged test results — 4/4 passing against real Postgres) and `apps/workers-cf`; `apps/workers-cf` bundles and resolves its declared bindings via real `wrangler deploy --dry-run` (twice — once on wrangler 3.x, confirmed again after upgrading to 4.x since the docs referenced are v4-era); `apps/web`'s existing Node build (`next build`, `turbo run typecheck`) is unaffected. `vinext check` against `apps/web` is real output, not a guess.

**Not verified — no real Cloudflare resources exist yet to test against:** the Queue consumer has never received an actual message (no queue, no Hyperdrive config, no R2 bucket created — all still placeholder IDs in `wrangler.jsonc`); Hyperdrive's actual behavior against a real external Postgres is unverified; the R2 binding's `.put()` call has never run; nothing has been deployed (`wrangler deploy` only ever run with `--dry-run`).
